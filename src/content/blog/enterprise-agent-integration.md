# 企业接入 Agent：CLI、Skill、Memory 应该如何分工

最近我在做一个业务 Agent 项目。由于项目本身不方便展开，文中的命令和工程设计主要使用 dws 作为例子，具体业务数据和内部流程均已省略。

项目开始时，我们也遇到了几个常见问题：已有 CLI 面向 Agent 要不要改，业务编排应该放在 CLI、Skill 还是 Agent，Skill 要不要覆盖所有场景，以及这套东西后续怎么维护。

做下来，我更关心的不是 MCP、A2A 或多 Agent 这些名词，而是一个具体问题：**哪些逻辑可以交给 Agent 判断，哪些逻辑应该做成稳定、可测试的能力。**

## 1. 面向 Agent 的 CLI 有什么不同

项目里的 CLI 原来主要给人和 CI/CD 使用。接入 Agent 后，stdin、stdout、stderr 和 exit code 这些基本约定没有变，但输出要求明显更严格。

### stdout 是数据契约

机器输出模式下，我们约定：

- stdout 只放结构化结果；
- stderr 放日志、进度条和诊断信息；
- exit code 表示进程是否成功；
- 成功和失败都使用稳定的数据结构。

例如，下面是我在本机使用 `dws v1.0.60` 查询一个只读命令的 Schema：

```bash
dws schema "calendar event get" --compact --format json
```

真实输出如下（参数部分未改动，其他字段做了节选）：

```json
{
  "agent_summary": "查询日程详情",
  "availability": "available",
  "canonical_path": "calendar.get_calendar_detail",
  "cli_path": "calendar event get",
  "confirmation": "not_required",
  "description": "查询日程详情",
  "effect": "read",
  "examples": [
    "dws calendar event get --id <EVENT_ID>",
    "dws calendar event get --id <EVENT_ID> --calendar-id primary"
  ],
  "idempotency": "idempotent",
  "parameters": {
    "calendar-id": {
      "description": "日历 ID (默认 primary 主日历)",
      "required": false,
      "type": "string"
    },
    "id": {
      "description": "日程 ID (必填)",
      "required": true,
      "type": "string"
    }
  },
  "risk": "low"
}
```

这个约定看起来普通，实际很重要。我们碰到过成功时输出 JSON，失败时却突然输出一段文本的情况。人能看懂，Agent 的解析逻辑却会直接失效。

错误也不能只写“执行失败”。至少要让调用方知道错误类型、是否适合重试，以及下一步可以检查什么。Agent 能不能自恢复，很大程度上取决于 CLI 有没有把这些信息说清楚。

### `--help` 不够，工具描述需要渐进加载

一个 CLI 承载的业务能力多了以后，不可能把所有命令和参数一次性塞进上下文。我们采用了分层加载：

```text
工具概览
  → 产品或分组
    → 单个命令的紧凑 Schema
      → 必要时再读取完整参数和约束
```

对应到 dws 的真实命令是：

```bash
dws schema --format json
dws schema calendar --compact --format json
dws schema "calendar event" --compact --format json
dws schema "calendar event get" --compact --format json
```

第一层只帮助 Agent 选工具；选中后才加载命令的参数、约束、风险和返回值。这样做不是为了取代 `--help`。`--help` 仍然适合人阅读，Schema 则给 Agent 提供稳定的机器契约。

dws 在这件事上给了我不少参考：Schema 不是另一份手写文档，而是尽量从真实命令声明和 Cobra 命令树装配出来。命令是否存在、接受哪些参数，最终仍以可执行 CLI 为准。否则帮助、Schema 和运行时很容易各写一套，时间久了必然漂移。

## 2. 业务编排放在哪里

这是项目里讨论最多的问题。现在我的划分比较直接：

| 位置 | 适合的情况 |
| --- | --- |
| CLI composite | 高频、稳定、可以测试的单产品流程 |
| Skill 脚本 | 参数会变，但执行步骤基本固定 |
| Skill SOP | 需要理解意图、处理歧义或跨产品选择 |
| Agent 自组合 | 一次性需求，暂时没有稳定模式 |

这几种方式可以同时存在，不需要只选一种。

![业务编排四层模型](https://img.alicdn.com/imgextra/i2/O1CN014zoDRWmsYFB3daAC_!!6000000005422-2-tps-1792-1024.png)

### 稳定流程放进 CLI

精度报告是一个典型例子。它内部要聚合需求、任务和精度数据，区分 Coding、文本和 VL 场景，还要处理任务重跑、废弃以及执行过程中的数据筛选。

这些逻辑已经稳定，而且每次生成报告都要执行。如果把它们写进 Skill，让 Agent 每次临时组合，不仅消耗更多上下文，也很难保证结果一致。因此我们把它作为一个业务命令提供给 Agent。

这里所说的“一个命令”不等于“只调用一次接口”。只要输入、输出和副作用对调用方是明确的，内部完全可以包含多步固定流程。

### 固定但变化较快的流程可以先放脚本

dws 的一键约会议脚本是一个容易理解的例子：

```text
创建日程
  → 添加参与人
  → 查询空闲会议室
  → 把会议室添加到日程
```

步骤固定，但脚本比修改核心 CLI 更轻，也可以提供 `--dry-run`。这适合仍在快速调整、但已经不需要 Agent 每一步做判断的流程。

脚本并不意味着可以不治理。只要会调用生产能力，仍然要有负责人、版本、测试、权限边界和发布方式。

![一键约会议流程](https://img.alicdn.com/imgextra/i4/O1CN01RT9TWB02D9L3daAC_!!6000000006504-2-tps-1792-1024.png)

### 有歧义的流程写进 Skill SOP

例如“给张三发邮件”，至少包含这些判断：

1. 先确认可用的发件邮箱；
2. 用户只给姓名时，查联系人，不能猜邮箱；
3. 调用发送命令；
4. 使用真实的消息 ID 查询发送状态；
5. 验证完成前，不能只凭一次命令返回就说“已经发送”。

这些内容适合放在 Skill 中。Skill 描述的是何时使用某个能力、前置数据从哪里来、遇到歧义怎么办、如何确认结果，而不是再抄一遍命令参数。

一句话概括：**Schema 说明命令怎么调用，Skill 说明什么时候调用以及失败后怎么办。**

### 新需求先让 Agent 组合

如果用户提出一个以前没有做过的组合，例如“找到张三最近发来的邮件，根据正文创建待办”，Agent 可以按需查询联系人、邮件和待办命令的 Schema，再完成组合。

这种方式适合探索，但不适合作为长期实现。如果同一种组合开始反复出现，而且步骤已经稳定，就应该逐步下沉到 SOP、脚本或 CLI composite。

还有一条边界：长时状态、跨系统事务、可靠重试、补偿和审批，不应该只靠 Agent 或本地 CLI 维持。它们仍然应该由后端工作流承担，CLI 只是入口。

## 3. Skill 的职责和几个误区

我们最开始很容易把 Skill 写成 CLI 使用手册，里面列满命令、参数和示例。这样做有两个问题：内容重复，而且 CLI 一改，Skill 马上过期。

现在我更倾向于让 Skill 只保留以下内容：

- 用户意图如何路由到合适的命令；
- 多个相似命令如何选择；
- 业务前置条件和禁止事项；
- 出错后的恢复路径；
- 结果如何验证；
- 哪些情况必须让人确认。

参数类型、必填项、互斥关系和返回结构由 Schema 提供。

![Skill vs Schema 职责划分](https://img.alicdn.com/imgextra/i2/O1CN01u1yVTLpo2jI3daAC_!!6000000006689-2-tps-1792-1024.png)

另外两个踩坑是：

1. 想用一个大 Skill 覆盖整个产品。结果是内容越来越长，Agent 每次都要加载无关信息；
2. 想一开始就写出“完美 Skill”。很多规则没有真实失败案例支撑，最后只是纸面上的完整。

比较有效的做法是先覆盖高频路径，再从失败记录和人工反馈中补规则。

## 4. Memory 怎么进入改进闭环

我不太相信依赖模型自己“越用越懂”。项目里的改进更多来自人工反馈：Agent 记录问题和当时的上下文，人对结果进行评论或修正，再决定这条经验应该留在哪一层。

例如，某次任务里人指出“只给姓名时不能猜邮箱”。这条反馈可以先作为有上下文的问题记录；如果后续反复出现，就加入 Skill SOP；如果已经能用确定性校验实现，则继续下沉到 CLI 或运行时门禁。

```text
执行失败或人工纠正
  → 保留上下文和原因
  → 判断是否重复出现
  → 更新 Skill / Eval
  → 能确定执行的部分继续下沉到 CLI
```

Memory 在这里更像待验证的经验，而不是无限增长的长期 Prompt。没有来源、适用范围和时效的信息，不应该直接变成全局规则。

![Memory 反馈改进闭环](https://img.alicdn.com/imgextra/i1/O1CN01p9GBeuxISKJ3daAC_!!6000000005378-2-tps-1792-1024.png)

[Warp 的实践](https://claude.com/blog/how-warp-builds-self-improving-agents-on-claude)也给过我启发：人负责评论和判断，Agent 根据反馈修改 Skill，再通过后续任务验证效果。这里真正起作用的不是模型“自我进化”，而是反馈被保存、评审并进入了可维护的工程资产。

## 5. 权限和确认必须落到运行时

Skill 里写“删除前请确认”并不能形成真正的保护。Agent 可能没有加载到对应段落，也可能选错命令。

对发送消息、修改权限、删除资源等操作，确认、权限和审计必须由运行时执行。Schema 可以把风险和确认要求告诉 Agent，但不能替代实际门禁。

![运行时权限门禁](https://img.alicdn.com/imgextra/i1/O1CN01KuWGDS8niRH3daAC_!!6000000004578-2-tps-1792-1024.png)

我们还尝试按不同角色限制可以使用的能力。这里的重点不是多 Agent，而是权限边界：即使多个角色最终调用同一个 CLI，也不应该天然拥有相同的命令范围和写权限。

## 6. 上线只是开始

做传统软件时，需求和使用路径通常相对确定。开发按照产品定义实现功能，用户通过页面、按钮和表单完成操作。一个版本上线，往往意味着这轮需求基本结束，后面进入维护阶段。

Agent 项目不太一样。上线之前，我们很难预先知道用户会怎么表达需求：同一件事有人说“看下今天的安排”，有人说“我下午有没有空”，也有人只丢过来一句“帮我约一下”。用户还会提出原来没有设计过的能力组合，或者在中间结果不符合预期时临时改变目标。

因此，上线不是验收终点，而是第一次拿到真实需求的开始。只有在实际使用中，才能看到：

- 用户真正想解决什么问题；
- 同一个意图有哪些不同问法；
- Agent 经常选错哪些相似命令；
- 哪些前置条件总被遗漏；
- 哪些临时组合已经变成了高频流程。

以前的软件更像一套“死”的规则：入口、路径和结果都由开发提前定义。Agent 软件则是“活”的，它在服务用户的过程中持续暴露问题，也给我们留下了改进的材料。

这里的“活”不是指模型会自己变好。每一次改进仍然需要工程闭环：记录失败及上下文，整理用户的真实问法，补充 Skill 和 Eval，再把已经稳定的逻辑下沉到 CLI 或工作流。没有这套闭环，上线后积累的只是更多对话，而不是更好的软件。

![传统软件与 Agent 软件的对比](https://img.alicdn.com/imgextra/i4/O1CN01lnk4DzgMkKJ3daAC_!!6000000004747-2-tps-1792-1024.png)

## 7. 这套 Agent 到底带来了什么

回头看，这个项目最直接的收益有两个：

- 用户可以通过自然语言找到自己关注的数据；
- 原来只能在特定系统里完成的查询，可以从 IM 等入口发起。

但如果 Agent 只覆盖流程中的一个局部，它带来的提升其实有限。很多时候只是给原有工具换了一个自然语言入口，底层流程和组织协作方式没有变化。

我现在更看重另外一件事：借着 Agent 接入，把原来只对人友好的 CLI 补成稳定的机器契约，把散落在人脑里的流程写成可维护的 Skill，并把重复出现的组合逐步下沉为可测试的能力。

这部分工作不显眼，却决定了 Agent 能不能从演示走到日常使用。
